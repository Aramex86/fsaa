Adoption guide

How to bring FSAA into an existing codebase without a big-bang rewrite.

scope: new and existing appsworks with React, Next.js, Vite

Use FSAA when

  • Several teams ship to one frontend codebase
  • Page blocks outgrow folders and review fights start
  • You want layering enforced by lint, not by memory

Don't use FSAA when

  • Single-page prototype with a short lifespan
  • Team of one or two with a stable tiny structure
  • Project is a library, not an app
Enforcement

Do not adopt FSAA without the ESLint boundary config. Rules that live only in a document decay within weeks; rules that fail CI survive refactors.

Migration notes

Order matters: boundaries first, moves second, promotions last.

  1. Add the lint rules, change nothing else. Start with zones for shared and entities; every existing violation becomes a visible diff, not a debate.
  2. Name the layers. Create empty features/, entities/,shared/ top folders next to your routes.
  3. Move design tokens and utils to shared. Zero-risk moves; imports update mechanically.
  4. Slice the biggest page blocks into features. One block per PR, ui/model/api only when each part exists.
  5. Extract entities with models. Move types + data access that 2+ features need; keep public APIs via index.ts.
  6. Graduate UI last. Only after step 5 do you have consumers to justify shared/ui molecules — apply the graduation pattern retroactively.

Review checklist

  • ✓ Imports point strictly downward — no layer skipping.
  • ✓ Feature-to-feature imports go through public APIs only.
  • ✓ shared/ui contains zero domain words (boundary test passed).
  • ✗ No atoms/molecules folders inside features — promote instead.
  • ✗ No new organisms tier, no widgets layer resurrection.
  • ✗ No pre-promoted “reusable” UI with a single consumer.
Tip

Run the checklist as part of the PR template for the first month — after that the lint config catches most of it automatically.

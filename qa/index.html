Q&A — hard questions, straight answers

The questions this methodology must survive — collected in a review session that attacked FSAA the way a skeptical tech lead would. No dodging: each answer is the position the docs and the templates actually implement.

Q“Isn’t this just an opinionated FSD preset with a new name?”

Yes to the assembly — and this is written in the README, not hidden. But a preset is something you install; a methodology is something that obligates. FSAA ships the three decision rules as mechanical artifacts: a lint config that rejects upward and cross-feature imports, a folder contract the generator follows, and a boundary test that settles review debates with one question.

A blog post describes. A methodology obligates — after the post is forgotten, the lint rule still fails the build. That difference is the product.

Short answer

The value is not the name; it is that the rules keep working after you stop remembering them.

Q“One maintainer, zero adoption — why bet a frontend on you?”

Honest: the risk is real and the docs name it. Three mitigations: the code is MIT with no lock-in — if the project dies, everything stays yours; the rules compact into a ~20-minute read, so a team onboarded without me; and the artifacts (templates, lint config) are plain config files your senior engineers already understand.

Adoption grows from working boundary cases, not promises — the placement-issue flow in CONTRIBUTING is the intended first contact.

Short answer

You are not betting on a person — you are copying two files and three rules you can read over coffee.

Q“Your production proof is behind NDA — what can actually be verified?”

The internal tool (financial accounting, managers/director/accounting as daily users) validates the rules under real load — but the code cannot be shown. So the claim was made verifiable differently: this documentation site is itself built on FSAA — features/entities/shared, thin routes, boundary-tested imports. Open the repo and inspect a working Next.js App Router layout that follows every rule.

Both starter templates ship the same structure with lint enforcement — the architecture is inspectable, forkable, and copyable into a project on Monday.

Short answer

NDA hid the proof — so an inspectable one was built on top of the docs.

Q“The graduation pattern: who decides, and what stops copy-paste drift?”

Told as a story, because the mechanics are simple:

Week 1 — ProjectCard lives inside features/projects-overview/ui/. Normal: every feature owns its UI.

Week 3 — the orders feature needs a similar card. It cannot import it from projects (cross-feature imports are a lint error). So the developer copies the file into features/orders-overview/ui/. The copy is legal — one duplicate is allowed on purpose: a real second user just appeared, and that fact is now visible in the codebase.

Week 4+ — the two cards keep evolving in parallel. If they end up the same anyway, that is proof the component is genuinely shared. Now one pull request graduates it: ProjectCard moves to shared/ui/molecules/, BOTH features import it from the shared public API (the folder’s index.ts), and the two feature-local copies are deleted inside that same PR. CI plus lint verify nothing still points at the deleted paths.

Nobody “feels” anything: the trigger is the second feature (objective), the gate is the boundary test, the move is a single PR. Drift cannot hide — a third copy fails CI on arrival, because the only legal cross-feature sources are entities (data) and shared (UI).

Short answer

Second feature = trigger. Boundary test = gate. One PR = the move, with the old copies deleted inside it.

Q“Where do layouts, loading/error files, route groups and parallel slots go?”

The App Router itself is the pages layer — no _app/_pages renames. Root layout.tsx is the FSAA app layer (providers, global config); section layouts and loading.tsx/error.tsx are page-composition wrappers; route groups are allowed while import directions stay intact; a parallel-route @slot references a feature and never implements one.

The full mapping is codified on the architecture page — and enforced by the starter’s ESLint config.

Short answer

Slots reference features — route files never grow business logic.

Q“What does adopting FSAA honestly cost an existing codebase?”

The methodology is incremental by design: features keep their flat ui/ folders from day one — no atomic reorganization inside features is required to start. The first real steps are (1) add the alias set, (2) turn on the boundary lint in warn mode for a sprint, then error mode, (3) run the boundary test on new components only.

What is deliberately NOT promised: a no-pain rewrite of a legacy tree. Migration stories live in the adoption guide; a rewrite is the wrong lens — graduation applies to components, not to sprints.

Short answer

Start with one sprint of warn-mode lint; graduation applies to components, not to big-bang rewrites.

Three things FSAA adds

01

The graduation pattern

Feature UI lives flat in features/<name>/ui/. It is promoted to shared/ui only after a second feature actually reuses it.

02

The boundary test

One question decides shared vs feature: could the component be described without business vocabulary? Generic DataTable passes; projectColumns does not.

03

No widgets layer

Large compositions are features, not a UI level. Container/presentational split happens at the export level, not in the filesystem.

Positioning

Position

“FSAA is not a new architecture theory. It is a practical, opinionated assembly of two proven methods — Feature-Sliced Design and Atomic Design — with the missing decision rules added. We do not claim a revolution.”

✔

Used in production on an internal financial accounting tool with real daily users (managers, director, accounting).

FSAA plays natively with Next.js App Router

FSD in Next.js collides with the router: app/ is taken, so teams rename layers to _app/_pages. FSAA needs none of that — the App Router itself is the pages layer. Route files stay thin (import → render), and layouts, loading.tsx/error.tsx, route groups and parallel-route slots are composition-layer concerns: a slot references a feature, it never implements one.

The same layers and the same ESLint boundaries ship for plain React (Vite 7 + react-router) in a second template — one methodology, two runtimes, no _app/_pages prefixes anywhere.

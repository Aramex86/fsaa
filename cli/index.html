Core rules · FSAA docs

CLI — one command to an FSAA app

npm create fsaa@latest downloads an official starter, renames it to your project, installs dependencies with pnpm, and ends with a green contract drift-check as proof. Zero runtime dependencies — plain Node 20+.

The commands

The package on npm is create-fsaa, so the standard npm create fsaa convention works. The binary inside is just fsaa.

create-fsaa — every command
CommandWhat it does
npm create fsaa@latestThe scaffold: interactive prompts (name, template next|vite). The package on npm is named create-fsaa, so the create-* convention works.
npx create-fsaa my-appSame scaffold, positional name (create-app convention).
fsaa init --name my-app --template viteNon-interactive: full flags. Without a TTY the defaults (my-app / next) apply automatically.
fsaa g <slice-name>Generate the canonical pair (entity + feature + thin route) inside an existing FSAA app. Slices are kebab-case.
fsaa helpThe help screen above.

Scripts and CI — no prompts, no hanging

When the CLI runs from a script, there is no keyboard. So it does not wait: missing answers fall back to defaults (my-app, template next) — and it says so in the log, once:

Note the -- after npm create fsaa@latest: everything after it goes into the CLI itself (npm’s separator, same as npm create vite). For deterministic pipelines pin BOTH values explicitly; the run ends with the same green drift-check as an interactive one.

The name — as it actually happened

npm renamed us before we shipped

The package was built as fsaa — and npm rejected the name at publish time with a 403: “Package name too similar to existing packages (fs, flat, gsap, …).” The typosquat-protection policy cannot be argued with, so the industry convention solved it: create-fsaa, which makes npm create fsaa work. Same day the first published version crashed on load (a backtick inside a template-literal) — fixed in the next release within an hour, and the whole story is this section.

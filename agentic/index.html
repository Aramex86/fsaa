Core rules · FSAA docs

AI agents — the contract, the checks, the procedures

An AI agent working on an FSAA codebase is not a trust question, it is an engineering question. The starter templates ship a machine-readable contract, a check that fails when docs and code drift apart, and step-by-step procedures an agent can follow without a human in the loop.

Why agents need a contract

An agent has no memory of your discussions, no sense of what is load-bearing and what is decoration. Left with a plain README, it will put UI wherever it fits, call fetch inside component trees and reformat a lockfile, all in one PR. FSAA answers with a contract the agent can read and the CI can enforce — the same rules, one source of truth.

The contract: AGENTS.md

Every rule in AGENTS.md carries a check marker. A rule without a working check fails CI — a rule nobody verifies is a suggestion, and suggestions rot within weeks. The file covers the package-manager decision, layer and UI placement, import boundaries, data access, file paths and the PR flow (~50 lines, machine and human readable in one sitting).

Drift-check — the enforcement

The green case: every contract rule verified on every PR. The check runs in CI (.github/workflows/) and locally in under a second:

Three ways it goes red — and each message tells you exactly what broke. The third one is the newest (v4.4): relative imports that leave your slice are resolved like a bundler resolves them, because a plain ../.. regex cannot tell an illegal cross-slice hop from a legal dive down to entities:

The rule behind the check

A rule with no check is red, a check with no rule is red. This came out of a real bug: the “which package manager is in charge” fact lived in three places at once, and the CI went red ten seconds after a push that contained zero application lines. v4.4 also closes the parity gap the other way — ESLint and the drift-check now catch exactly the same violations, barrels (index.ts) included.

Procedures — what the agent runs, step by step

The templates ship agents/ — numbered, one-screen procedures with a verify step that must end green. Each mirrors a real workflow from building FSAA itself.

Navigation for external agents

AGENTS.md is written for the agent working on the templates. For an agent dropped into an app built from a template, the navigation file agents/where-ui-goes.md gives the layer map, the three boundaries and a checklist to run before writing any code:

References, not copies

The navigation file links to the procedures; it does not duplicate them. A duplicated decision is a second copy that will silently rot — the docs website itself rotted once because nobody enforced its structure.

Getting started

Four steps, in order — none of them optional, all of them verified by the checks above:

  1. Scaffold your app with the CLI — npm create fsaa@latest (the create-fsaanpm package; while the registry release is pending: npx github:Aramex86/fsaa init). It downloads a starter, installs deps, and ends with a green drift-check as proof.
  2. Generate slices inside the project: fsaa g <slice-name> (or npx create-fsaa g …).
  3. Cold start with agents/run-stack.md — install, dev up, green checks.
  4. Point your agent (Claude Code, Cursor, …) at AGENTS.md and agents/; keep main protected PR-only — drift-check + lint + tests run on every PR.
✔

Self-demonstrating: this docs site itself is built with FSAA — pages as features, the page registry as an entity, navigation filtered through a feature, imports enforced by the same ESLint boundaries.

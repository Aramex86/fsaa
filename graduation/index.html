Core rules · FSAA docs

The graduation pattern

FSAA's answer to premature abstraction: UI earns its place in shared/ui, it is not born there.

Motto

Features own their UI until it earns sharing.

The flow

Stage 1 — feature-owned

Component lives in one feature. Used there, tuned there, free to change without negotiation across teams.
features/accounting/ui
  └─ PeriodPicker.tsx   // single consumer
imports: entities, shared
→a 2nd feature needs it
→ promote

Stage 2 — shared/ui

Component graduates: moves to shared/ui/molecules, gets a public API via index.ts, its API is now a small contract.
shared/ui/molecules
  ├─ index.ts
  └─ PeriodPicker/    // graduated
boundary test: pass // see below

Features own their UI until it earns sharing.

Boundary test for shared

If I removed this component from the app entirely, could it still be described without mentioning users, orders, or projects?

PassGeneric props, no domain words: Table, Callout, CopyButton, PeriodPicker.
FailAny domain term in props or markup: InvoiceRow, AccountStatus.
  • ✓ pass Renaming the feature does not touch the component.
  • ✗ fail The component imports from entities or features below.

The pattern applied to this site

01

Button stayed generic

Used by home, roadmap and repo-cta. Passes the boundary test — no docs vocabulary inside — so it lives in shared/ui/atoms.

02

ComparisonMatrix is a feature

It knows method-profile entity data. Feature-owned; promotion would only happen if a second page needed the same matrix.

03

LayerStackExplorer is a feature

Renders fsaa-layer entity knowledge. Not generic UI — its props vocabulary is the stack itself.

04

DataTable graduated early

Row/column generic, zero domain words. Used by two pages plus a feature — exactly the case the graduation pattern was designed for.

No pre-promotion

Do — wait for the second consumer

  • Keep Stage 1 as long as it is convenient.
  • Change the API freely while owned by one feature.
  • Promote with a rename-free move + index.ts barrel.

Don't — guess reusability

  • “We'll probably reuse it” is not a consumer.
  • Don't parameterize a one-consumer component.
  • Don't hoist a domain component into shared/ui.
Anti-pattern

Pre-promoted UI rots twice: feature teams wrap it in props soup, shared owners hesitate to change a “public” contract. Graduation keeps both costs zero while there is exactly one consumer.

The pattern is deliberately asymmetric: entering shared/ui is cheap but gated, leaving it is rare and expensive. Promote on proof, not prediction.
